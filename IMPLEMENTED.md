Honest snapshot of what actually runs today. A phase is only marked
**Implemented** if its acceptance scenario runs end-to-end; if part of it
works it's **Partial**; **Started** means only groundwork exists. This file
only lists phases with real work — phases with no code yet aren't listed
here at all; they'll be added, one at a time, as each is actually built.

| 1 | Voice I/O Foundation | **Partial** | Mic capture, TTS playback, and chunked/interruptible speech work. **Offline STT/TTS fallback added 2026-08-16** (`src/vortex/voice/stt.py`, `voice/tts.py`): cloud stays the default/primary path — Google Web Speech (STT) and edge-tts (TTS) are tried first, exactly as before, unchanged behavior when online — and only fall back to a local model on a *network-reachability* failure specifically, not on "the service was reached but didn't like this audio/text": STT falls back on `sr.RequestError` only (never `sr.UnknownValueError` — that means Google understood the attempt fine, the audio just wasn't clear, and downgrading to a worse local model for that would be a downgrade, not a fallback); TTS falls back on `aiohttp.ClientConnectionError`/`asyncio.TimeoutError` only (never edge-tts's own `EdgeTTSException` family — that means the service *was* reached and returned something odd, a different, retriable problem). Offline STT uses `faster-whisper`'s `base.en` model (CPU, `int8`); offline TTS uses `piper-tts`'s `en_US-lessac-medium` voice — both gated by one kill switch, `VortexConfig.offline_fallback_enabled` (`VORTEX_OFFLINE_FALLBACK_ENABLED`, default on), and both degrade to a logged "unavailable" rather than crashing if the packages aren't installed or a model isn't cached yet (same probe-and-degrade contract as `documents.py`'s `_ocr_available`). Both engines lazy-load as an in-process singleton (loaded/downloaded at most once, not per call) and are explicitly warmed up (downloaded + loaded) from `main.py`'s existing `_warm_up_models()` hook — off the critical path, while the network is presumably still up — so the first real outage doesn't also have to be the first download attempt. **What's verified, and how:** (1) the exception-routing logic itself — `tests/unit/test_stt.py`/`test_tts.py`, 17 new tests, mocking `recognize_google`/`edge_tts.Communicate` to raise each exception type and asserting the offline path is/isn't called accordingly; full suite (`tests/unit/`) is 55/55 passing, the 38 pre-existing tests unchanged. (2) The offline engines for real, called directly through the actual `SpeechToText`/`TextToSpeech` classes (not mocks): a real edge-tts-synthesized clip ("turn off the living room lights") decoded to 16kHz PCM and run through `_recognize_offline()` came back `'turn off the living room lights.'` — correct. `_synth_offline()` on a real sentence produced a real ~185KB WAV, played for real through pygame (`[diag] offline _play took 4.19s`, in line with the sentence's natural length). **Not verified:** an actual simulated network outage inside the live app (`recognize_google`/edge-tts genuinely timing out end-to-end) — this dev environment doesn't have a clean way to sever outbound network for one process without affecting the sandbox itself, so the *trigger condition* is verified only via the mocked-exception unit tests above, not a real severed connection. **Real latency/quality trade-offs observed, not hidden:** offline is slower and less accurate than cloud, as expected for a fallback, not a replacement. STT: cold model construction in a fresh process ran 3.8-8.1s across repeated runs (real, measured, not smoothed over — CTranslate2 init cost varies run to run) before any real-time work is even absorbed by the startup warm-up; per-call inference once warm was sub-2s on a ~2s clip. `base.en` was chosen over `tiny.en` specifically because warm inference for the two was NOT meaningfully different (tiny.en 0.5-1.5s vs base.en 0.9-1.4s, measured back-to-back) — no latency reason to accept `tiny.en`'s known-worse accuracy. TTS: piper voice load ~4-11s cold (absorbed by warm-up), ~2-5s per-sentence synthesis once warm — both real (not synthetic-silence) generations were reviewed by ear via pygame playback and matched the input text. `faster-whisper`/`piper-tts` are a new optional extra, `voice-offline` (not bundled into `voice` or `all`) — split out deliberately for two verified reasons: real added install weight (`ctranslate2`+`av`+`piper-tts` wheels combined, before either engine's model weights are even downloaded) and `piper-tts` being GPL-3.0-or-later, a different license than the rest of this project's dependencies. No device-selection UI, no formal provider-interface abstraction (`speak`/`capture_command` are concrete methods with an offline branch inside them, not swappable adapters — a deliberate judgment call matching this project's existing "don't introduce an interface split before there's a second *implementation* driving the need for one" pattern, see both classes' docstrings). |
| 2 | Desktop & OS Automation | **Partial** | Open/close named apps, bulk-close with a protected-process allowlist, confirmation gating before shutdown/restart/close-all, lock-system (no confirmation needed - trivially reversible, loses no work). **File operations added (2026-08-16):** `src/vortex/files.py` - voice-triggered list ("list files", "list files in downloads"), search ("find file X", "search for files containing Y" - filename/glob matching only, not the content search Phase 5's RAG stack already does over document text), move, copy, and rename, plus delete via `send2trash` (Windows Recycle Bin, never a permanent `os.remove`). Scoped ONLY to the same three directories `documents.py` already resolves against (Desktop/Documents/Downloads, reusing `documents.SEARCH_DIRS` rather than a second, possibly-diverging path policy) - every resolved path is verified to actually live under one of those directories before being touched, so no `..`, absolute-path, or symlink voice input can reach anywhere else (`PathNotAllowedError` otherwise). Delete/move/rename are gated behind the same `self.awaiting_confirmation` yes/no flow already used for shutdown/restart/close-all; copy is not confirmation-gated - a deliberate, narrower judgment call (see `files.py`'s docstring) since it can't destroy or rename a pre-existing file, and move/copy/rename all now structurally refuse to overwrite an existing file at the destination (`FileExistsError`) rather than silently clobbering it. **Structured audit log added:** `src/vortex/audit.py` (`AuditLog`) writes one JSON object per line - timestamp, action, target, outcome, plus optional details - to a separate file (`logs/audit.jsonl` by default, `VORTEX_AUDIT_LOG`-overridable) for consequential actions: file delete/move, app close, shutdown/restart, and every confirmation prompt together with its eventual outcome (`prompted`/`executed`/`declined`/`failed`). This is additional to, not a replacement for, the existing plaintext `self.log()`/`logging.info()` calls, which are unchanged. **Capability registry added:** `execute()`'s regex-based if/elif chain was mechanically restructured into a list of `{name, matcher, handler, destructive, description}` entries it iterates in the same order as before - dispatch infrastructure only. It does **not** add authorization or policy: `destructive` is descriptive metadata, not an enforced gate (e.g. `close_named_app` - "close X" - is marked `destructive: True` but, exactly as before this change, still runs immediately with no confirmation prompt, unlike bulk-close). Every pre-existing voice command was verified, via `tests/unit/test_registry.py`, to still route to the exact same handler after the rewrite; 104 `pytest` tests pass, including 4 new files covering registry dispatch, file-op path-safety/no-overwrite/send2trash behavior, the audit log's JSON-lines format, and end-to-end confirmation gating for the new destructive commands. Still no general permission/policy model beyond the fixed three-directory scope and the fixed list of confirmation-gated actions, no audit-log rotation/retention, and search remains filename-only (not a content index). **Fixed bug:** "shutdown vortex" set internal flags to stop the worker/audio threads but never stopped the `pystray` tray icon, so `icon.run()` (blocking the main thread) never returned and the process lingered as a zombie - stopped listening/responding, but never actually exited. `stop()` now stops the icon too, unifying the voice-triggered shutdown and the tray's Exit item into one real shutdown path. |

| 5 | Memory, Knowledge & Production RAG | **Partial** | Two separate pieces, not yet unified: (1) `src/vortex/memory.py` — conversation history persists across restarts in a local SQLite database instead of an in-RAM list; still no retrieval over it, just chronological recall. **Migration onto the Postgres+Qdrant stack was considered and deliberately scoped out this pass (2026-08-16)** — it's a genuinely separate, involved piece of work (a second Qdrant collection for conversation turns, an embedding step on every turn, retrieval wiring into `main.py`'s conversation flow, all while guaranteeing SQLite stays authoritative and the existing chronological fallback keeps working unchanged if Postgres/Qdrant are down) and attempting it in the same pass as the RAG hybrid-search work below risked doing it hastily; `memory.py` is untouched, still exactly as described above. (2) `src/vortex/rag.py` — the real Postgres+Qdrant stack from the master blueprint, used specifically for document question-answering: documents are chunked, embedded locally (`nomic-embed-text` via Ollama), and indexed in Qdrant, with Postgres as the transactional source of truth for chunk text/metadata. A targeted question retrieves only the relevant chunks instead of truncating a long document. Runs against local, self-hosted Postgres and Qdrant (native Windows installs, not Docker — see README setup). Degrades gracefully to the old truncated-whole-document approach if Postgres/Qdrant aren't running. **Hybrid dense+sparse search and reranking added (2026-08-16):** `retrieve()` now pulls a candidate pool from Qdrant's dense cosine search *and* BM25 keyword search (`rank_bm25`, pure-Python, only depends on numpy already pinned for the wake-word stack) over the same document's full chunk text, combines them with Reciprocal Rank Fusion (rank-only combination — chosen specifically because cosine similarity and BM25 scores live on incomparable scales, so a weighted blend would need ad-hoc normalization RRF avoids entirely), then reranks the fused top-10 with a keyword-overlap/exact-substring heuristic before truncating to the final top-k. **Deliberately not a cross-encoder reranker:** checked `sentence-transformers`' actual install footprint before deciding (`pip install sentence-transformers --dry-run`) — it resolves a 122MB torch wheel (Windows, cp311) plus transformers/tokenizers/safetensors, and a real reranker model would be a *further* separate download at first use. That's a real mismatch for an otherwise fully local, lightweight app, so a cheap keyword-overlap heuristic was used instead — see `rag.py`'s module docstring for the full reasoning. Both stages are independently off-switchable (`VORTEX_RAG_HYBRID_SEARCH`, `VORTEX_RAG_RERANK`, new `VortexConfig` fields `rag_hybrid_search`/`rag_rerank`, both default on). **Real trade-off, not free:** hybrid mode adds one Postgres query per uncached document (fetching the BM25 corpus, then cached in memory) plus BM25/RRF/rerank CPU work on top of the existing embed-and-search round trip — not measured against a hard latency budget, but it is strictly more work per question than the previous dense-only path. **Verified:** `retrieve()`'s signature and return shape are unchanged, so `main.py`'s one call site needed zero edits. 22 new unit tests (`tests/unit/test_rag_hybrid.py`) cover BM25 scoring, RRF fusion, the keyword-overlap reranker, and `RagStore.retrieve()`'s wiring against mocked Postgres/Qdrant — including a synthetic (explicitly simulated, not live) case showing a dense-only top-3 that misses an exact-keyword chunk get recovered into the hybrid top-3 by fusion. **Live end-to-end verified** against real Postgres, Qdrant (started temporarily via its scheduled task, stopped again after), and Ollama (`nomic-embed-text`): ingested a synthetic multi-chunk facility-manual document containing several near-identical "rotating access code" paragraphs (deliberately adversarial — same sentence template, different code) plus a paraphrasable fact; the full pipeline (dense search → BM25 → RRF fusion → rerank) ran correctly end-to-end and returned the right chunk. Honest finding from that live run: `nomic-embed-text`'s dense-only search *also* ranked the correct exact-code chunk first in every live trial run here — evidently strong enough at literal substring/subword overlap that it didn't need rescuing by BM25 in this specific case, so the dramatic dense-miss-hybrid-catches scenario was only demonstrated in the synthetic unit test, not forced live within this session's testing budget; hybrid search did not regress anything either (paraphrase query for the semantic fact still worked via the dense signal). **Incidental bug found and fixed while testing this:** `ensure_ingested()` re-ingesting a changed document deleted the old Postgres chunk rows but never told Qdrant to drop the matching points, so a document's *previous* version's chunk vectors stayed indexed forever, silently polluting future dense search for that document — `ensure_ingested()` now calls `qdrant.delete()` scoped to that `document_id` before upserting the new points (best-effort: a failed delete doesn't block re-ingestion, just leaves stale points for next time), covered by 2 new unit tests. |

## A capability the blueprint didn't spell out in detail, but is real today

**Self-trained wake-word model** (`tools/wakeword/`): a from-scratch pipeline
that synthesizes training audio (edge-tts across ~20 voices), extracts
embeddings via openWakeWord's shared preprocessor, trains a small MLP
classifier, runs a hard-negative-mining pass over long synthetic audio
streams, and exports the result as a standalone ONNX model matching
openWakeWord's exact I/O contract. This is a narrow, supervised,
single-classifier training loop — not general model training — but it's a
concrete first instance of "VORTEX can train its own models."

## Honest gaps versus the blueprint's own Phase 6 requirements

- *"Wake detection must not require network access"* — true for wake
  detection itself (fully local ONNX). STT/TTS now have an offline fallback
  (`faster-whisper`/`piper-tts`, see Phase 1's row above) that engages
  specifically on a network-reachability failure, but the fallback's trigger
  condition is verified only via mocked exceptions in unit tests, not a real
  severed network connection against the live app end-to-end — so "a network
  outage silences VORTEX" should be read as "should no longer, pending a real
  live outage test," not as a fully closed gap yet.
- *CPU/RAM budget on 8GB-class hardware* — never measured. Should be profiled
  before calling Phase 6 done.
- *Barge-in with real human voice, not just the trained wake phrase* — only
  "Hey Vortex" is ever checked as an interrupt trigger; generic words like
  "wait" or "stop" do nothing, by design (a VAD-based "any speech interrupts"
  approach would make VORTEX constantly interrupt itself, since its own TTS
  output is speech too). Near-field self-noise (mic hears VORTEX louder than
  the user while it's talking) is mitigated via `VORTEX_TTS_VOLUME` but not
  solved - true acoustic echo cancellation would be required to solve it
  fully, and isn't implemented.
